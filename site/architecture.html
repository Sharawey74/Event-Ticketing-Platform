Engineering Deep-Dive

How zero-oversell actually works.

A modular monolith with seven bounded contexts, an atomic Redis inventory guard, and a strict layered architecture — chosen for specific engineering reasons, not defaults.

System architecture

Next.js talks to a Spring Boot backend over a stateless JWT-authenticated REST API. PostgreSQL is the source of truth; Redis holds inventory counters, distributed locks, and the JWT denylist; RabbitMQ offloads QR generation and email so the request path never blocks on them.

Reservation flow — the concurrency-critical path

1. Client          ── POST /api/v1/bookings ──► BookingService
2. BookingService  ──► Redis     acquire per-user distributed lock
3. BookingService  ──► Redis     re-check availability (TOCTOU guard)
4. BookingService  ──► Redis     reserveSeat() — atomic Lua floor guard

  SEATS AVAILABLE                       SOLD OUT
  5. Redis decremented, success         5. Redis rejects (floor guard)
  6. Postgres atomic conditional        6. Client ◄── 409 Conflict
     UPDATE (available_count -= n)
  7. Postgres INSERT Booking
     (state=RESERVED, expires=+5m)
  8. Client ◄── 201 Created

9. BookingService  ──► Redis     release lock

Concurrency & data integrity

MechanismImplementation
Oversell preventionA Redis Lua script performs the availability check and decrement as one atomic operation — verified by 100 concurrent threads against a 50-seat tier: exactly 50 succeed, 0 oversold.
DB/cache consistencyThe PostgreSQL inventory mirror is written via a single atomic conditional UPDATE … WHERE available_count >= :qty, not a read-modify-write.
TOCTOU guardAvailability is checked once before acquiring the lock, then re-checked inside the lock before committing.
Optimistic locking@Version on Booking, TicketTier, and Event; ObjectOptimisticLockingFailureException maps to a clean 409, not a raw 500.
State machineAn 11-state Spring State Machine (one instance per request) governs the booking lifecycle, rejecting illegal transitions like checking in a cancelled booking.
IdempotencyStripe webhook delivery is deduplicated via a database UNIQUE constraint, not a race-prone existsBy… pre-check; booking creation requires an Idempotency-Key header.

Reliability

  • Multi-replica-safe scheduling — the reservation-expiry job acquires a distributed lock before running, safe across multiple backend instances.
  • Structured, traceable logging — a correlation ID propagates from the inbound HTTP request through every service log line via MDC.
  • Async offloading — QR generation and transactional emails dispatch through RabbitMQ (with dead-letter queues) instead of blocking the request thread.

Security posture

Access control uses two independent layers: RBAC decides whether a role may call an endpoint; object-level authorization separately decides whether the specific resource belongs to the caller.
